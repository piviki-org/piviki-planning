Piviki, the Vietnamese community lending library in Tampere

How the Piviki system will work

One small server holds every book, account and rule. A free static website, the librarian tool and the scanning script all talk to it, and the running bill stays near 5 EUR a month plus email.

Status, 2 November 2026: the design is finished and nothing is built yet. Five independent reviews found real problems. Those fixes are in the design, but the reviews have not been re-run on the revised version. Some technical assumptions are still to be proven, and five questions need the founders.

The system in one picture

Only piviki-core holds data or applies library rules. That is the idea everything else follows: the patron site and the scanning script can ask core to do something, but they can never decide whether it is allowed.

ProjectWhat it isWho uses it
piviki-coreThe library itself: data, rules, emails, the librarian tool, built with Payload and Next.jsLibrarians directly; everyone else through its API
piviki-patronThe public website: browse, search, reserve, see your loans. Screens only, no rulesParents
piviki-scanTurns photos of the donated books into draft catalogue records for a librarian to reviewFounders, for the initial load

Following one reservation

A reservation moves through six possible states, and a queue place is simply a reservation in the queued state. Keeping one record for both means the queue and the shelf can never disagree about who is next. AD-2, AD-3

What a parent sees for a book comes from one calculation: copies on the shelf, minus reservations waiting for one. A book with spare copies shows as available, and otherwise as on loan. It shows as unavailable only when every copy is lost.

Example titleCopies on shelfQueued or reservedFreeParent sees

An overdue book blocks reserving, queueing and renewing until it is returned. That is the only consequence of being late, and the database has no field for fees or fines. AD-2, AD-4

How families' data is protected

  • Kept out entirely: data about children, and the pickup address, which is shared only in the chat groups. AD-14
  • Before a parent can reserve: a verified email, an adult tick and acceptance of the current usage policy, on every sign-up path including Google. AD-8
  • Separate doors: parents reach only the public API. The librarian tool sits behind a second sign-in check, and a parent's session cannot open it. AD-5, AD-7
  • Deletion that holds up: an automated test deletes a patron, then searches a full database dump for any trace. A restore from backup deletes those accounts again before the app starts. AD-14, AD-17
  • Backups: encrypted nightly, kept 30 days in an EU bucket, readable only with a key both founders hold offline. AD-17
  • Who else sees patron data: only OVHcloud, Cloudflare, the email provider and, for parents who choose it, Google. Each one is named in the privacy notice. AD-18

These are internal targets, and the library opens when the software is ready. If a milestone slips, features are cut in a fixed order: ISBN lookup, self-renewal, due-date reminders, then the English interface. Reservations, the queue, the pickup loop, check-in, the ready-for-pickup email and the overdue block are never cut.
